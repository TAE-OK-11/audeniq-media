# 통합 전후 성능 비교

통합 전 바이너리와 통합 후 바이너리를 같은 머신에서 비교했습니다. 결론부터 말하면 두 엔진 모두 성능이 떨어진 케이스는 없고, 출력도 바이트 단위로 같습니다.

- 통합 전: audeniq-qc `cf44360`(자체 프로필), audeniq-photo `586ff22`(자체 프로필)
- 통합 후: 이 브랜치. audeniq-qc는 `--release`, photo는 `--profile release-photo`

## 측정 방법

- **머신**: Intel Xeon 2.1 GHz, 4 vCPU 공유 VM(AVX-512·SHA-NI·VPCLMULQDQ 지원). 노이즈가 약 ±5%로 큽니다.
- **시간**: 기준·신규 바이너리를 라운드마다 번갈아 실행했습니다. CPU를 고정했고(qc는 코어 3, photo는 코어 1~3), 지표는 CPU 시간(user+sys)과 벽시계 시간입니다. 표에는 라운드별 비율(신규/기준)의 중앙값과 부트스트랩 95% 신뢰구간을 적었습니다. 구간이 1을 포함하면 차이가 유의하지 않다는 뜻입니다.
- **명령어 수**: valgrind cachegrind의 Ir입니다. 같은 바이너리는 몇 번을 실행해도 값이 같아서, 노이즈에 묻히는 1% 미만의 차이까지 판정할 수 있습니다. 단, valgrind 안에서는 SHA-NI와 AVX-512가 숨겨지기 때문에 해시는 이식형 경로로 측정됩니다.
- **출력**: 모든 케이스에서 stdout과 출력 파일 바이트가 기준과 같은지 비교했습니다. 아래 "출력 비결정성"의 2건만 예외입니다.
- **입력 코퍼스**: 오디오는 240초 16/44.1 음색+잡음, 24/48, 180초 24/96 핑크 노이즈를 WAV·AIFF·FLAC·ALAC·TTA로 준비했습니다(명령어 수 측정은 15~20초 클립). photo는 3000/1400px 사진형 JPEG(베이스라인·프로그레시브·Adobe RGB·CMYK)·PNG, 텍스트 표지(OCR), QR 합성 표지, 스캔형 3쪽·텍스트 1쪽 PDF, 69 MB WAV입니다.

## 통합 과정에서 고친 성능 문제

측정하면서 발견한 저하는 모두 고친 뒤 위 결과를 냈습니다.

1. **빌드 프로필.** 공통 `release`에 photo 설정(fat LTO, codegen-units=1)을 쓰면 qc의 ALAC 변환+QC CPU 시간이 약 13% 늘었습니다. 반대로 LTO를 빼면 photo OCR이 약 11% 느려졌습니다. 그래서 `release`(qc)와 `release-photo`로 나눴습니다.
2. **panic 방식.** `release`를 unwind로 두면 unwind 런타임 심볼 때문에 qc 프로세스 시작마다 동적 링크 비용(약 4천 명령어)이 늘었습니다. `release`는 통합 전처럼 abort로 되돌렸습니다. photo는 `catch_unwind`가 필요해 `release-photo`에서 unwind를 쓰고, abort 프로필로는 빌드되지 않도록 `compile_error!`로 막았습니다.
3. **JSON(`media-json`).** 원래 qc의 작은 보고서용 구현이라, serde_json(1.0.151)을 대신하기엔 출력이 느렸습니다(실수 4.8배, 문자열 1.45배). 출력 바이트는 그대로 두고 다음을 고쳤습니다.
   - 문자열: 이스케이프를 serde_json과 같은 256바이트 조회표로 판별하고, 8바이트 단위(SWAR)로 검사합니다. 최종 UTF-8 재검증을 생략합니다(구성상 UTF-8, debug에서는 검사).
   - 정수: 4자리씩 변환하고, 슬라이스 출력에서 인라인되도록 했습니다.
   - 실수: Rust `{:e}` 결과를 다시 해석하던 방식을 **Ryu `d2d` 직접 포팅**으로 바꿨습니다. 공통 경로에서는 자릿수를 8/4/2개씩 묶어 제거합니다. 2^53 미만 정수값과 소수 1~3자리 값에는 빠른 경로를 둡니다(유일 후보일 때만 사용하고, 그 외에는 Ryu).
   - 출력 버퍼의 초기 용량을 128바이트로 잡았습니다(serde_json과 같음).

   명령어 수 기준으로 serde_json 1.0.151 대비 문자열 보고서는 0.87배, 정수는 약 1.05배, 일반 실수(고정밀)는 약 1.4~1.9배입니다. 실수만 남는 차이는 serde_json의 zmij 알고리즘이 Ryu보다 빠르기 때문입니다. 실제 photo 보고서는 문자열·정수가 대부분이라 프로세스 단위로는 위 표처럼 같거나 적습니다. qc는 통합 전에도 같은 media-json을 썼으므로 이번 변경은 qc에 순수한 개선입니다.

## 출력 호환성

- **qc**: 18개 시간 케이스와 20개 명령어 수 케이스 모두 바이트가 동일합니다. JSON의 실수는 serde_json 1.0.140(ryu)과 같고, 무작위·구조화 값 1.1억 개로 대조했습니다.
- **photo**: 모든 케이스가 동일합니다. 예외가 하나 있습니다. 통합 전 photo가 쓰던 serde_json 1.0.151은 |x| ≥ 1e16인 실수의 양수 지수를 `1e+16`처럼 썼고, 통합 후에는 qc 기준인 `1e16`으로 씁니다. JSON 값으로는 같고 자릿수도 1.1억 개 모두 일치합니다. 메타데이터에서 1e16 이상의 실수는 사실상 나오지 않습니다.
- **출력 비결정성**(통합 전부터): `sanitize 3000 png`와 `pdf-render`는 병렬 압축 분할 때문에 실행할 때마다 PNG 바이트가 다릅니다. 기준 바이너리도 마찬가지입니다. 디코딩한 픽셀은 기준과 신규 모두 같습니다.
